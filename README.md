Задача 2: Логи
Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
минимальные требования к приложениям, сбор логов из stdout;
гарантированная доставка логов до центрального хранилища;
обеспечение поиска и фильтрации по записям логов;
обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
возможность дать ссылку на сохранённый поиск по записям логов.
Обоснуйте свой выбор.



Ответ 

Для сбор логов Filebeat агент разворачивается на каждом хосте . Он читает логи контейнеров из stdout/stderr, не требуя изменения кода приложений. Filebeat отслеживает файлы и события, буферизирует данные и отправляет их в Logstash или напрямую в Elasticsearch.

Обработка и маршрутизация Logstash, он принимает логи от Filebeat, выполняет фильтрацию, обогащение и нормализацию, после чего направляет данные в Elasticsearch. Logstash поддерживает буферизацию на диске и механизм подтверждений, что обеспечивает гарантированную доставку даже при кратковременных сбоях сети или недоступности Elasticsearch.

Хранение и поиск подходит Elasticsearch Распределённый поисковый движок с горизонтальным масштабированием. Индексирует логи в реальном времени, обеспечивая полнотекстовый поиск и фильтрацию по любым полям.

Визуализация и доступ Kibana веб-интерфейс для поиска по логам, построения дашбордов и сохранения поисковых запросов. Разработчики получают доступ через роли с ограничением по индексам. Сохранённый поиск можно превратить в ссылку и передать коллеге.


Задача 3: Мониторинг
Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

сбор метрик со всех хостов, обслуживающих систему;
сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
сбор метрик, специфичных для каждого сервиса;
пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.
Обоснуйте свой выбор.


Ответ 

Сбор метрик хостов Node Exporter разворачивается на каждом физическом или виртуальном хосте. Он экспортирует метрики CPU, RAM, HDD, Network в формате Prometheus через HTTP-эндпоинт /metrics.

Сбор метрик контейнеров/сервисов cAdvisor собирает метрики потребления ресурсов  по каждому контейнеру. Для метрик, специфичных для сервиса, приложение инструментируется клиентской библиотекой Prometheus.

Сбор и хранение Prometheus периодически «скрейпит» эндпоинты /metrics всех экспортёров и приложений. Данные хранятся в встроенной time-series базе.

Визуализация Grafana подключается к Prometheus как источнику данных. Она предоставляет гибкий интерфейс для построения запросов PromQL и визуализации в виде графиков, таблиц, heatmap, настройку панелей — можно создавать дашборды с произвольной компоновкой, использовать готовые шаблоны, Алертинг на основе пороговых значений метрик.
